# 软件任务汇报：数据流、载荷显示与算法验证

## 一、数据流载荷上传和下发

当前软件形成了统一的双向链路：

```text
传感器/状态上行：ROS/Gazebo → ROS WebSocket Gateway → Spring Boot → Vue/Unity WebGL
控制任务下行：Vue → Spring Boot → ROS WebSocket Gateway → ROS 任务/载具控制节点
执行结果回传：ROS /fleet/command_ack、任务状态 → Gateway → Spring Boot → Vue/Unity
```

### 1. 上行信息流

| 数据 | ROS/Gazebo 来源 | 网关载荷 | 后端实时主题 | 使用端 |
|---|---|---|---|---|
| 3+3 位姿 | `/world/heterogeneous_332/pose/info`、`/fleet/state` | `pose_frame` | `fleet.pose` | 二维态势、Unity WebGL |
| 任务状态 | `/capture/state`、实时护航状态机 | `mission_state` | `mission.state` | 任务中心、数据库 |
| 相机 | `/fleet/uplink/{device}/camera...` | `camera_frame` | `visual.camera` | 光电视觉、设备画中画 |
| 雷达航迹 | 融合与各艇 `/perception/.../radar/tracks` | `radar_frame` | `radar.overview` | 雷达态势页 |
| MID-360 点云 | `/perception/{device}/mid360/preview` | `pointcloud_frame` | `radar.overview` | 点云/雷达状态 |
| 视觉检测 | `/perception/usv_01/camera/affiliated_detections` | `visual_detection_frame` | `visual.detections` | 识别框与目标列表 |
| 控制结果 | `/fleet/command_ack` | `command_ack` | `control.ack` | 命令状态与任务状态机 |

位姿采用 ROS ENU，位置单位为米，四元数固定为 `[x,y,z,w]`。Unity WebGL 只做坐标转换和数字孪生显示，不生成权威运动状态。

### 2. 下行控制流

任务控制：

```text
START/PAUSE/RESUME/CANCEL_MISSION
→ Spring Boot 创建 commandKey 并记录 DISPATCHED
→ Gateway 发布 /fleet/base/operator_action
→ 围捕等待 /capture/state，护航等待实时算法状态
→ 达到预期状态后返回 STATUS_SUCCEEDED
→ 后端 ACK 协调器推进任务与批次数据库状态
```

单机控制：

```text
UAV_TAKEOFF/HOVER/RETURN/LAND、USV_DEPART/HOLD/RETURN/STOP
→ /fleet/control_lease
→ /fleet/command
→ 真实 ROS agent 执行
→ /fleet/command_ack
→ 后端和浏览器收到真实结果
```

任务 ACK 不在“刚发布 Topic”时提前成功。任务权威状态异常时立即失败，默认 12 秒未确认则超时失败。

## 二、不同机艇载荷传感器信息显示

网关按设备 ID 独立缓存与发送传感器载荷：

```text
radar_device_ids      ↔ radar_tracks_topics
pointcloud_device_ids ↔ pointcloud_topics
camera_id             ↔ camera topic
```

每帧携带来源标识：

- 雷达：`frame.device_id`
- 点云：`frame.data.vehicle_id`、`stream_id`
- 相机：`camera_id`
- 位姿：`vehicles[].id`

前端可按 `usv_01..03`、`uav_01..03` 分别显示设备位姿、相机、检测和传感器在线状态。融合雷达使用 `fleet_fused` 标识，不与独立艇载雷达混合。

ROS launch/SDF 已给 `usv_01..03` 分别创建独立的 RGL MID-360 实体传感器；每艘艇均有独立 Gazebo 原始点云、ROS `PointCloud2` 桥接、预处理、TF 和 `/perception/{device}/mid360/preview` 输出，前端可按设备区分三路真实仿真点云。

2026-08-17 实测三路 preview 单帧分别包含 2279、2368、2576 点；WebSocket 实际收到的三路非空 `pointcloud_frame` 分别包含 1078、1169、1188 点，来源标识依次为 `usv_01`、`usv_02`、`usv_03`。

## 三、算法仿真验证

### 1. 本次算法替换

算法来源：`/home/wl/桌面/护航守卫_三维单目标_Python39(1).py`。

原本地 `ESCORT_GUARD` 是以 `friendly_ship` 为中心的固定 USV/UAV 双环目标。本次替换为新算法的实时适配版：

- 敌方目标进入感知半径后锁存威胁；
- 在敌方目标与高价值目标之间计算严格内部核心阻断点；
- 使用匈牙利最小代价分配选择核心守卫、翼侧守卫和后向支援；
- 3 UAV + 3 USV、无预备队时分配为 `1 核心 + 2 翼侧 + 3 支援`；
- 按真实 Gazebo 位姿持续更新导航目标；
- 通过核心到位和翼侧到位比例判断 `FORMING/GUARDING`；
- 角色、阻断点、感知距离和就绪度随 `mission_state` 上报。

原文件中的 Matplotlib 显示、内部虚拟机艇运动、内部虚拟目标生成和按键控制没有接入正式链路。真实适配器不伪造位姿，`friendly_ship`、`enemy_ship` 和 3+3 机艇均以 ROS/Gazebo 为权威来源。

实现文件：

- `UnityProject/unity_ws/WebSocketBridge/escort_guard_algorithm.py`
- `UnityProject/unity_ws/WebSocketBridge/unity_websocket_bridge.py`

### 2. 验证层次

| 层次 | 本次状态 | 验证内容 |
|---|---|---|
| 算法核心单元验证 | 已完成 | 阻断点、感知半径、角色数量、目标点、真实位姿模式 |
| ROS/Gazebo 真实机艇链路验证 | 已完成（软件仿真） | 真实 Gazebo 位姿输入、3+3 `/fleet/command` 输出、任务状态；UAV 未起飞时先下发真实 TAKEOFF |
| 虚拟 UAV/USV 节点验证 | 按要求暂不执行 | 不启动额外虚拟节点，不以虚拟节点结果作为本次结论 |
| 实物硬件在环/下水验证 | 待硬件与场地 | 同一控制/遥测协议切换真实设备适配器后验证 |

“真实机艇算法验证”在当前软件环境中指真实 ROS agent + Gazebo/PX4 控制闭环，不等同于实物下水试验；实物试验需单独记录硬件、通信链路、安全员和场地结果。
